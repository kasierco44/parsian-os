# معماری کلان PARSIAN OS

## 1. هدف و دامنه
PARSIAN OS سکوی یکپارچه عملیات پارسیان قطعه است. هسته مرکزی به‌صورت افزونه اختصاصی WordPress روی `pgtparts.ir` اجرا می‌شود و چهار تجربه مستقل مشتری، فروشنده، حسابداری و مدیریت را به داده و سرویس‌های مرکزی متصل می‌کند.

## 2. تصمیم قطعی معماری
- **WordPress Plugin = هسته مرکزی و مرجع داده (System of Record):** منطق کسب‌وکار، کاربران، نقش‌ها، مجوزها، گردش تأیید، داده‌های CRM/فروش/مالی/انبار، گزارش‌های مرکزی و API در افزونه اختصاصی نگهداری می‌شود.
- **API-first:** تمام کلاینت‌ها فقط از REST API نسخه‌بندی‌شده و HTTPS استفاده می‌کنند؛ اتصال مستقیم کلاینت به دیتابیس ممنوع است.
- **Modular Monolith:** افزونه در شروع ماژولار است؛ جداسازی سرویس‌ها فقط با دلیل فنی و بدون شکستن قرارداد API انجام می‌شود.
- **Offline-first clients:** هر کلاینت داده محلی، صف عملیات پایدار و موتور همگام‌سازی دارد.
- **توسعه تدریجی و بدون جایگزینی کور:** افزونه نصب‌شده و پروژه‌های موجود حفظ می‌شوند؛ هر تغییر پس از بررسی کد واقعی، تست و مسیر بازگشت انجام می‌شود.

## 3. چهار محصول مستقل
1. **PARSIAN Customer (Android):** کاتالوگ و اطلاعات مجاز مشتری، پیش‌نویس سفارش، سوابق و اسناد قابل مشاهده. داده‌های لازم برای کار آفلاین cache می‌شوند.
2. **PARSIAN Seller (Android):** CRM، مشتریان تخصیص‌یافته، سرنخ، تماس/بازدید، پیش‌فاکتور، سفارش، پیگیری و ثبت دریافت در وضعیت «در انتظار همگام‌سازی/تأیید».
3. **PARSIAN Accounting (Web + Windows):** پنل وب و برنامه دسکتاپ مستقل ویندوز با قابلیت آفلاین، ثبت پیش‌نویس اسناد، دریافت/پرداخت، چک، طرف حساب، سررسید و گزارش‌های محلی با برچسب زمان آخرین همگام‌سازی.
4. **PARSIAN Management (Web + Windows):** پنل وب و برنامه دسکتاپ مستقل ویندوز برای داشبورد، کاربران، نقش‌ها، اهداف، گردش تأیید، تنظیمات، گزارش‌ها و نظارت بر همگام‌سازی.

هر چهار محصول مستقل نصب/اجرا می‌شوند. وب‌پنل‌های حسابداری و مدیریت نیز به‌صورت PWA قابل نصب طراحی می‌شوند؛ نسخه Windows بسته دسکتاپ مستقل دارد و برای کار آفلاین به سرویس وب وابسته نیست.

## 4. نمای منطقی
```text
Android Customer ─┐
Android Seller ───┤
Accounting Web/PWA├── HTTPS REST API v1 ── WordPress + PARSIAN OS Plugin
Management Web/PWA┤                         ├─ Domain Modules
Windows Accounting┤                         ├─ Auth / RBAC / Approval / Audit
Windows Management┘                         ├─ Custom WP Tables (MySQL/MariaDB)
        │                                    └─ Sync API / Device Registry
        └── Local DB + Durable Outbox              │
             (SQLite / IndexedDB)                  └── Central Data + Backups
```

## 5. فناوری و ذخیره‌سازی
- **مرکز:** WordPress Plugin با PHP سازگار با نسخه پشتیبانی‌شده WordPress و جداول اختصاصی با پیشوند امن؛ استفاده از MySQL/MariaDB مطابق دیتابیس نصب وردپرس.
- **API:** مسیر نسخه‌بندی‌شده مانند `/wp-json/parsian-os/v1/`، احراز هویت امن، مجوز سمت سرور، pagination، فیلتر، validation و idempotency.
- **Android:** Kotlin/Jetpack Compose یا فناوری موجود پس از بررسی سورس واقعی؛ پایگاه داده محلی SQLite از طریق Room و صف همگام‌سازی WorkManager.
- **Web/PWA:** رابط مشترک فارسی RTL؛ IndexedDB برای داده‌های محلی و Service Worker برای shell و منابع استاتیک.
- **Windows:** پوسته دسکتاپ Tauri با رابط مشترک وب، پایگاه داده SQLite محلی و سرویس Sync داخلی. نصب و اجرای محلی مستقل؛ اتصال اینترنت فقط برای همگام‌سازی و ورود/تأییدهای نیازمند سرور لازم است.
- **تاریخ و پول:** زمان استاندارد در پایگاه داده؛ نمایش شمسی. مبالغ با integer/decimal دقیق و واحد صریح تومان یا ریال؛ float برای پول ممنوع.

## 6. قرارداد همگام‌سازی آفلاین
هر کلاینت باید این اجزا را داشته باشد:
- Local database برای داده‌های مجاز و موردنیاز نقش.
- Durable Outbox برای عملیات ارسال‌نشده؛ با خروج از برنامه پاک نمی‌شود.
- Inbox/Delta Cursor برای دریافت تغییرات سرور از آخرین نقطه همگام‌سازی.
- شناسه یکتای دستگاه و شناسه یکتای هر عملیات.
- Idempotency key برای جلوگیری از ثبت تکراری در retry.
- ثبت وضعیت هر عملیات: محلی، در صف، ارسال‌شده، پذیرفته‌شده، نیازمند تأیید، ردشده یا دارای تعارض.
- retry با backoff و گزارش خطای قابل فهم.
- تعارض‌ها طبق سیاست دامنه‌ای؛ هرگز بازنویسی خاموش آخرین تغییر.

### سیاست تعارض
- یادداشت و پیگیری غیرمالی: امکان ادغام یا نگهداری نسخه‌ها.
- اطلاعات مشتری: کنترل نسخه و حل تعارض قابل مشاهده؛ تغییر حساس نیازمند مجوز.
- قیمت، موجودی، اعتبار و مانده: داده مرجع سرور است؛ داده آفلاین فقط snapshot با زمان آخرین دریافت است.
- فاکتور، دریافت، پرداخت، چک و گردش موجودی: عملیات آفلاین ابتدا پیش‌نویس/در انتظار بررسی است؛ ثبت قطعی، تأیید پرداخت و اثر نهایی حسابداری فقط پس از اعتبارسنجی و پذیرش سرور.
- حذف: tombstone و مجوز؛ حذف فیزیکی بی‌ردپا ممنوع.

## 7. هویت، امنیت و نقش‌ها
- ورود یکپارچه با توکن کوتاه‌عمر و refresh token قابل ابطال؛ توکن هر دستگاه مستقل و قابل لغو.
- کنترل مجوز سمت سرور برای هر endpoint و هر رکورد؛ UI به‌تنهایی مرز امنیتی نیست.
- حساب فروشنده به مشتریان تخصیص‌یافته محدود؛ فروشنده به موجودی انبار دسترسی ندارد مگر مجوز صریح.
- حسابدار به عملیات مالی/انبار مطابق مجوز؛ مدیر به تنظیمات و تأییدهای مجاز.
- داده محلی حساس رمزگذاری شود؛ قفل برنامه، خروج امن، پاک‌سازی داده دستگاه از راه دور در صورت پشتیبانی.
- TLS، محدودسازی نرخ، audit log، اعتبارسنجی فایل و ورودی؛ اسرار در Git ذخیره نشوند.

## 8. مرز مسئولیت آفلاین
کار آفلاین به معنی تضمین تازگی داده یا تأیید قطعی نیست. کلاینت می‌تواند داده cache شده را بخواند و عملیات مجاز را به شکل محلی ثبت کند. هر صفحه باید وضعیت آفلاین و زمان آخرین همگام‌سازی را نشان دهد. عملیات وابسته به قیمت لحظه‌ای، اعتبار، موجودی یا تأیید مدیر تا دریافت پاسخ سرور «قطعی» نمایش داده نمی‌شوند.

## 9. استقرار و بازیابی
- افزونه مرکزی روی WordPress staging قبل از production آزموده می‌شود.
- مهاجرت دیتابیس افزونه نسخه‌بندی‌شده و قابل بازگشت است.
- پشتیبان دیتابیس و فایل‌ها رمزگذاری‌شده و بازیابی آن عملاً آزمایش می‌شود.
- نسخه‌های Android، Windows و افزونه دارای شماره نسخه و حداقل نسخه API سازگار هستند.
- انتشار مرحله‌ای: توسعه، تست، staging، سپس production با برنامه rollback.

## 10. تصمیم‌های باز برای مرحله اجرا
- بررسی سورس واقعی افزونه نصب‌شده و پروژه Android موجود پیش از هر بازنویسی.
- تعیین نسخه دقیق PHP، WordPress، MySQL/MariaDB و سیاست میزبانی از محیط واقعی.
- انتخاب قطعی Kotlin/Compose یا حفظ فناوری Android فعلی پس از دریافت سورس.
- تعیین روش بسته‌بندی و امضای Windows installer و Android APK.
- طراحی جزئیات conflict resolution، رمزگذاری SQLite و بازیابی دستگاه.
