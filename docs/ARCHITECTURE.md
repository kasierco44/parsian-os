# معماری کلان PARSIAN OS

## 1. هدف و دامنه
PARSIAN OS سکوی مادر برای یکپارچه‌سازی عملیات پارسیان قطعه است؛ نه بازنویسی فوری همه ابزارهای موجود. سامانه باید CRM و فروش، مالی، انبار، تولید، نیروی فروش دورکار، بازاریابی و قابلیت‌های هوش مصنوعی را با مرزبندی ماژول‌ها پشتیبانی کند.

## 2. اصول معماری
1. **Modular Monolith در شروع:** یک Backend قابل استقرار با مرزهای دامنه‌ای روشن؛ جداسازی سرویس‌ها فقط در صورت نیاز اثبات‌شده.
2. **API-first:** تمام کلاینت‌ها از API نسخه‌بندی‌شده استفاده می‌کنند.
3. **Cloud-first:** Backend و پایگاه داده روی سرور ابری مدیریت‌شده/ VPS امن؛ کلاینت‌ها به سرور مرکزی متصل می‌شوند.
4. **Offline-tolerant clients:** اپ موبایل باید صف عملیات محلی و همگام‌سازی کنترل‌شده داشته باشد؛ تعارض‌ها نباید بی‌صدا بازنویسی شوند.
5. **Auditability:** عملیات مالی، تغییر دسترسی، تغییر موجودی و تأییدها باید قابل ردیابی باشند.
6. **Incremental migration:** سامانه‌های فعلی مانند پارسیان‌یار و مخزن Android موجود حفظ می‌شوند تا اتصال یا مهاجرت با آزمون و برنامه انجام شود.

## 3. پشته فناوری پیشنهادی
- Backend: Python + FastAPI؛ انتخاب نهایی پس از نمونه اولیه و ارزیابی تیم.
- Database: PostgreSQL؛ مهاجرت schema با ابزار migration نسخه‌بندی‌شده.
- Cache/queue: Redis در صورت نیاز عملیاتی؛ در فاز اول اجباری نیست.
- Web UI: وب‌اپ فارسی RTL با فناوری نهایی پس از نمونه اولیه رابط.
- Mobile: Flutter گزینه پیشنهادی برای Android؛ تصمیم قطعی پس از بررسی نیازهای دستگاه و تلفن.
- Desktop: ابتدا وب واکنش‌گرا/PWA؛ بسته Windows در صورت نیاز واقعی و پس از ارزیابی.
- Automation: n8n برای گردش‌کارهای بیرونی، نه منطق حیاتی تراکنش مالی.
- AI Core: لایه مستقل برای مدل‌ها و ابزارها با مجوزدهی، ثبت ورودی/خروجی و تأیید انسانی.

## 4. نمای منطقی

```text
Android / Web / Windows
          |
     API Gateway
          |
  FastAPI Application
  |       |        |
Identity CRM/Sales Finance/Inventory/Production
  |       |        |
 Domain Services + Approval + Audit
          |
      PostgreSQL
          |
 Integrations / Queue / n8n / AI Core
```

این نمودار مفهومی است؛ سرویس‌های مجزا در شروع الزاماً فرایند یا سرور جدا ندارند.

## 5. مرز ماژول‌ها
هر ماژول مالک مدل‌ها و قواعد دامنه خود است. ارتباط بین ماژول‌ها از طریق سرویس‌های داخلی و رویدادهای دامنه انجام می‌شود؛ دسترسی مستقیم و کنترل‌نشده به جداول ماژول دیگر ممنوع است.

## 6. استقرار محیط‌ها
- `local`: توسعه روی رایانه توسعه‌دهنده با داده ساختگی.
- `test`: تست یکپارچه و پذیرش؛ بدون اطلاعات واقعی مگر داده ناشناس‌سازی‌شده.
- `staging`: شبیه محیط نهایی برای آزمون انتشار.
- `production`: محیط عملیاتی با دسترسی محدود، TLS، پشتیبان‌گیری و پایش.

تنظیمات و اسرار از متغیرهای محیطی/مدیریت اسرار دریافت می‌شوند و در مخزن ذخیره نمی‌شوند.

## 7. اصول رابط کاربری
- فارسی و راست‌به‌چپ به‌صورت پیش‌فرض.
- تاریخ شمسی در نمایش؛ ذخیره‌سازی تاریخ/زمان استاندارد و timezone-aware.
- واحد پول در هر صفحه و API صریح باشد؛ تبدیل تومان/ریال در لایه ارائه انجام شود.
- نقش‌ها و مجوزها در UI فقط برای تجربه کاربری اعمال می‌شوند؛ کنترل نهایی همیشه سمت سرور است.

## 8. تصمیم‌های باز
- انتخاب قطعی چارچوب وب و Desktop.
- انتخاب ارائه‌دهنده VPS، منطقه میزبانی و سیاست بازیابی بحران.
- روش احراز هویت چندمرحله‌ای و ارائه‌دهنده پیامک.
- نیاز نهایی به Redis و صف پیام.
- جزئیات اتصال PortsIP/تلفنچی و دستگاه‌های Android.

هر تصمیم قطعی باید در `docs/decisions/` به‌صورت ADR ثبت شود.
