# آفلاین، همگام‌سازی، فایل‌ها و کاتالوگ محصولات

## تصمیم معماری
کلاینت فروشنده باید Offline-First باشد. سرور ابری مرجع نهایی داده‌هاست؛ پایگاه داده عملیاتی PostgreSQL و فایل‌های باینری (عکس محصول، کاتالوگ PDF، پیوست‌ها) در فضای ذخیره‌سازی شیءگرا (S3-compatible یا سرویس معادل) با نسخه‌بندی و پشتیبان‌گیری نگهداری می‌شوند. فایل باینری در PostgreSQL ذخیره نمی‌شود؛ فقط metadata، مجوز، checksum، نسخه و کلید ذخیره‌سازی ثبت می‌شود.

## تجربه آفلاین فروشنده
- ورود اولیه و دریافت بسته امن داده‌های مجاز کاربر هنگام آنلاین بودن؛ نشست آفلاین محدود به دستگاه ثبت‌شده و مدت اعتبار سیاست مدیر.
- مشاهده مشتریان تخصیص‌یافته، اطلاعات تماس، سوابق لازم، وظایف، کاتالوگ و تصاویر دانلودشده.
- ایجاد/ویرایش پیش‌نویس پیگیری، یادداشت، بازدید، سفارش و پیش‌فاکتور محلی؛ هر فرمان یک UUID idempotency_key، device_id، client_created_at و نسخه مبنا دارد.
- عملیات در Outbox پایدار محلی با وضعیت pending / syncing / synced / conflict / failed نگهداری می‌شود. بستن برنامه یا خاموش‌شدن گوشی صف را حذف نمی‌کند.
- هنگام اتصال، Sync Worker با backoff و محدودیت شبکه، ابتدا تغییرات ارسالی را ارسال و سپس تغییرات سرور را با cursor دریافت می‌کند. پاسخ هر فرمان با شناسه یکتا تطبیق داده می‌شود؛ ارسال مجدد نباید سند تکراری بسازد.
- داده مالی/اعتباری و موجودی در حالت آفلاین فقط پیش‌نویس یا درخواست ثبت است؛ تأیید نهایی، تخصیص شماره رسمی فاکتور، وصول وجه، ثبت چک و تغییر موجودی فقط با پاسخ موفق سرور انجام می‌شود.
- تعارض‌ها بی‌صدا overwrite نمی‌شوند. برای فیلدهای مستقل merge کنترل‌شده؛ برای قیمت، تخفیف، اعتبار، تسویه و موجودی، سرور مرجع است و تعارض به صف بررسی مدیر می‌رود.
- نمایش واضح «آفلاین»، «در انتظار ارسال»، «همگام‌شده» و «نیازمند بررسی» به کاربر.

## همگام‌سازی و API
پیشنهاد قرارداد:
- GET /api/v1/sync/bootstrap: نسخه سیاست دستگاه، داده‌های مرجع و cursor اولیه.
- POST /api/v1/sync/push: batch فرمان‌های Outbox؛ پاسخ per-item شامل accepted / duplicate / conflict / rejected.
- GET /api/v1/sync/pull?cursor=...: تغییرات مجاز کاربر از آخرین cursor.
- POST /api/v1/devices/register و revoke: ثبت/لغو دستگاه و کلید/نشست دستگاه.
- تمام endpointها احراز هویت، مجوز object-level، rate limit، audit و idempotency دارند.
- cursor بر اساس ترتیب تغییرات سرور است، نه ساعت موبایل. زمان کلاینت صرفاً metadata است.
- حذف‌ها با tombstone همگام می‌شوند تا رکورد حذف‌شده در دستگاه قدیمی دوباره ظاهر نشود.

## محصولات و مدیریت رسانه
- پنل مدیر برای ایجاد/ویرایش محصول: SKU، نام، دسته، مدل خودرو، نوع وایر/قطعه، توضیح، وضعیت فعال، ترتیب نمایش، نسخه کاتالوگ و قیمت‌های دارای تاریخ اعتبار.
- گالری چندعکسی برای هر محصول، تصویر اصلی، ترتیب، متن جایگزین، اندازه/نوع فایل، checksum، نسخه و تاریخ انتشار.
- بارگذاری فقط از مسیر مجاز مدیر/کاربر دارای مجوز؛ اعتبارسنجی MIME واقعی، اندازه، اسکن بدافزار، نام‌گذاری تصادفی و عدم اجرای فایل آپلودی.
- فایل اصلی و نسخه‌های بهینه‌شده (thumbnail و اندازه موبایل) در Object Storage خصوصی؛ دسترسی با URL امضاشده و زمان‌دار یا API کنترل‌شده. مسیر عمومی قابل حدس ممنوع.
- تغییر عکس یا اطلاعات محصول نسخه جدید ایجاد می‌کند. کلاینت manifest کاتالوگ را با ETag/version بررسی و فقط فایل‌های تغییرکرده را دانلود می‌کند.
- امکان انتخاب «دانلود کاتالوگ برای استفاده آفلاین» با نمایش حجم و فضای موردنیاز؛ پاک‌سازی cache قدیمی پس از تأیید دانلود نسخه جدید.
- حذف محصول/عکس ابتدا soft-delete و tombstone؛ پاک‌سازی فایل پس از دوره نگهداری و اطمینان از نبود ارجاع.
- فروشنده فقط کاتالوگ، قیمت و محتوایی را می‌بیند که مدیر برای نقش/منطقه/کانال انتشار داده است؛ موجودی انبار برای نقش فروشنده پنهان می‌ماند مگر مجوز مستقل داده شود.

## امنیت و نگهداری
- داده محلی حداقلی، رمزگذاری‌شده و وابسته به دستگاه؛ خروج از حساب یا revoke دستگاه، دسترسی آفلاین را قفل می‌کند.
- عکس‌ها و اسناد حساس در cache عمومی گالری سیستم ذخیره نمی‌شوند.
- سرور: PostgreSQL + Object Storage خصوصی + نسخه پشتیبان رمزگذاری‌شده و آزمون بازیابی دوره‌ای.
- سیاست نگهداری، سقف حجم هر فایل، quota هر کاربر/شرکت و ثبت audit برای upload/publish/delete.
- هیچ اطلاعات واقعی یا secret در Git ذخیره نمی‌شود.

## ترتیب تحویل
1. تثبیت schema و API محصولات، رسانه و manifest.
2. افزودن sync cursor، device registry و idempotent push/pull به Backend.
3. افزودن دیتابیس محلی و Outbox رمزگذاری‌شده در اپ Android.
4. اتصال مشتری/پیگیری/سفارش/پیش‌فاکتور به صف آفلاین.
5. پنل مدیریت محصول و بارگذاری عکس؛ انتشار نسخه کاتالوگ.
6. آزمون قطع اینترنت، ارسال تکراری، تعارض دو دستگاه، لغو دستگاه، فایل بزرگ، بازیابی بکاپ و ارتقای نسخه کاتالوگ.
7. انتشار آزمایشی و سپس اتصال به سرور عملیاتی پس از تعیین دامنه API و Object Storage.

## معیار پذیرش
- پس از دانلود اولیه، حالت پرواز اجازه مشاهده داده‌های مجاز و ثبت پیگیری/پیش‌نویس را بدهد.
- بستن اجباری اپ، restart گوشی و بازگشایی، Outbox را حفظ کند.
- پس از اتصال، هر فرمان دقیقاً یک بار در سرور اثر کند؛ ارسال مجدد duplicate نسازد.
- مدیر با انتشار عکس/قیمت/توضیح جدید، کلاینت آنلاین را به‌روز کند و کلاینت آفلاین در اتصال بعدی فقط delta را بگیرد.
- لغو دسترسی دستگاه مانع sync و ورود آفلاین بعدی شود.
- هیچ‌گاه فروشنده به داده انبار یا مشتری تخصیص‌نیافته دسترسی نگیرد.
