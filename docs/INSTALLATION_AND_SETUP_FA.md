# راهنمای نصب و راه‌اندازی PARSIAN OS

تاریخ بازبینی: ۱۴۰۵/۰۸/۲۸  
مخزن: `kasierco44/parsian-os`  
شاخه توسعه: `feature/parsian-final-core-platform`  
PR: #21 (Draft)

> **وضعیت انتشار:** این شاخه نسخه توسعه است، نه بسته تأییدشده Production. راهنما برای نصب در محیط آزمایشی (Staging) نوشته شده است. تا پیش از عبور از تمام آزمون‌های پذیرش، روی سایت اصلی `pgtparts.ir` نصب نکنید.

## ۱. اجزای سامانه

| جزء | مسیر مخزن | وضعیت فعلی |
|---|---|---|
| هسته و افزونه WordPress | `wordpress/parsian-final/` | کد افزونه و REST API موجود؛ نصب و مهاجرت Staging باید اجرا و تأیید شود |
| پنل‌های وب | `web/parsian-panels/` و نسخه bundle در افزونه | رابط‌های نقش‌محور موجود؛ آزمون انتهابه‌انتها لازم است |
| اپ Android فروشنده | `android/`، flavor برابر seller | سورس و workflow ساخت موجود؛ APK فقط پس از موفقیت CI قابل تحویل است |
| اپ Android مشتری | `android/`، flavor برابر customer | سورس و workflow ساخت موجود؛ APK فقط پس از موفقیت CI قابل تحویل است |
| برنامه Windows | `desktop/` | پوسته Tauri موجود؛ نصب‌کننده و تست VM هنوز تأیید نشده |
| Backend کمکی | `backend/` | سرویس FastAPI/PostgreSQL موجود؛ مرجع داده کلاینت‌ها همچنان REST افزونه WordPress است |

## ۲. پیش‌نیازهای محیط Staging

- دامنه یا زیردامنه آزمایشی با HTTPS معتبر؛ از نمونه‌ای مانند `staging.example.com` استفاده کنید.
- WordPress و PHP 8.2 یا بالاتر، با افزونه‌های استاندارد WordPress و دسترسی WP-CLI.
- MySQL/MariaDB سازگار با نسخه WordPress؛ فضای کافی برای نسخه پشتیبان.
- دسترسی مدیر WordPress و دسترسی SSH/پنل هاست.
- قبل از هر نصب/ارتقا: از **پایگاه داده و تمام فایل‌های WordPress** نسخه پشتیبان جداگانه بگیرید.
- روی Staging داده واقعی مشتری یا رمز/توکن Production قرار ندهید؛ از داده آزمایشی استفاده کنید.

## ۳. ساخت بسته افزونه WordPress

در GitHub مخزن را باز کنید و شاخه `feature/parsian-final-core-platform` را انتخاب کنید:

1. وارد Actions شوید.
2. workflow با نام **PARSIAN FINAL WordPress plugin package** را باز کنید.
3. آخرین اجرای مربوط به آخرین commit شاخه را انتخاب کنید.
4. فقط اگر وضعیت اجرای workflow برابر **Success** بود، artifact با نام `parsian-final-wordpress-plugin-dev` را دریافت کنید.
5. ZIP باید ساختار زیر را داشته باشد؛ پوشه افزونه باید مستقیماً در ریشه ZIP باشد:

```text
parsian-final/
  parsian-final.php
  includes/
  assets/
  tests/
```

6. اگر workflow شکست خورد یا artifact به commit قدیمی تعلق داشت، از آن ZIP استفاده نکنید. workflow را برای آخرین commit دوباره اجرا کنید.

این artifact، در صورت ساخت موفق، **بسته توسعه** است و موفقیت ساخت ZIP به‌تنهایی به معنی تأیید عملکرد مالی یا آمادگی Production نیست.

## ۴. نصب افزونه روی WordPress آزمایشی

1. وارد پیشخوان WordPress محیط Staging شوید.
2. از مسیر «افزونه‌ها ← افزودن افزونه ← بارگذاری افزونه»، فایل ZIP را انتخاب کنید.
3. نصب و سپس فعال‌سازی را انجام دهید.
4. اگر نصب یا فعال‌سازی خطا داد، ادامه ندهید؛ متن خطا و گزارش PHP را ثبت کنید.
5. پس از فعال‌سازی، مسیر REST زیر را با مرورگر یا ابزار API بررسی کنید:

```text
https://STAGING-DOMAIN/wp-json/parsian-final/v1/health
```

باید پاسخ معتبر JSON سلامت سرویس دریافت شود. اگر 404 دیدید، پیوندهای یکتا را یک‌بار ذخیره کنید و REST API و فعال‌بودن افزونه را بررسی کنید.

## ۵. حساب‌ها و نقش‌ها

نقش‌های تعریف‌شده در افزونه:

- مدیر (Manager): دسترسی مدیریتی و تأیید عملیات مجاز.
- حسابدار (Accountant): عملیات مالی و گزارش‌های مجاز.
- فروشنده (Seller): فقط سرنخ‌ها و مشتریان تخصیص‌یافته و امکانات فروش مجاز.
- مشتری (Customer): فقط اطلاعات حساب مشتری متصل‌شده.

حساب‌های کاربری را از پیشخوان WordPress بسازید و نقش مناسب را اختصاص دهید. حساب مشتری باید توسط مدیر به رکورد مشتری متصل شود. برای فروشنده، تخصیص مشتری را از مسیر پنل مدیر یا API مربوطه انجام دهید. با حساب فروشنده، عدم دسترسی به موجودی و مشتریان سایر فروشندگان را حتماً آزمایش کنید.

**رمز پیش‌فرض یا حساب مشترک نسازید.** برای هر نفر حساب جداگانه و رمز منحصربه‌فرد تعیین کنید.

## ۶. پنل‌های وب

پنل‌ها در افزونه مرکزی bundle شده‌اند و از مسیر پنل PARSIAN FINAL در WordPress در دسترس قرار می‌گیرند. آدرس دقیق منو پس از فعال‌سازی و با توجه به نسخه نصب‌شده بررسی شود.

آزمون اولیه هر نقش:

- مدیر: مشاهده داشبورد، تخصیص مشتری، صف تأیید Sync و خروجی پشتیبان.
- حسابدار: مشاهده دفتر روزنامه، تراز آزمایشی، دریافت/پرداخت، چک و مغایرت بانکی.
- فروشنده: مشاهده مشتریان تخصیص‌یافته، سرنخ‌ها و پیش‌فاکتورهای مجاز.
- مشتری: مشاهده فاکتورها، پیش‌فاکتورها و پرداخت‌های حساب متصل.

نتایج مالی را با اسناد آزمایشی و مانده‌های کنترل تطبیق دهید؛ صرف نمایش صفحه، صحت محاسبات را اثبات نمی‌کند.

## ۷. ساخت اپ‌های Android

نیازمندی‌ها: JDK 17، Android SDK Platform 35، Build Tools 35.0.0 و Gradle 8.7.

در پوشه `android` اجرا کنید:

```bash
gradle --no-daemon :app:assembleSellerDebug :app:assembleCustomerDebug
```

خروجی‌های مورد انتظار:

```text
android/app/build/outputs/apk/seller/debug/
android/app/build/outputs/apk/customer/debug/
```

یا از GitHub Actions workflow **PARSIAN FINAL Android debug builds** استفاده کنید و artifact با نام `parsian-android-debug-apks` را فقط پس از موفقیت همان اجرا دریافت کنید.

- APKهای Debug برای تست هستند؛ برای انتشار عمومی کافی نیستند.
- برای Release باید کلید امضای اختصاصی ساخته و فقط در GitHub Secrets یا محیط امن نگهداری شود؛ کلید و رمز آن را داخل مخزن commit نکنید.
- نصب روی دستگاه واقعی، ورود، خروج، انقضای توکن، قطع/وصل اینترنت، صف عملیات، دریافت رویداد و نقش‌های seller/customer را آزمایش کنید.
- API Root باید آدرس HTTPS سایت Staging باشد؛ HTTP پذیرفته نیست.

## ۸. ساخت برنامه Windows

پیش‌نیازها: Windows 10/11، Rust stable با MSVC، WebView2 Runtime و Tauri CLI نسخه 2.

در PowerShell:

```powershell
cd desktop
cargo install tauri-cli --version "^2" --locked
cargo tauri build --bundles msi,nsis
```

خروجی مورد انتظار در مسیرهای زیر است:

```text
desktop/src-tauri/target/release/bundle/msi/
desktop/src-tauri/target/release/bundle/nsis/
```

همچنین workflow **PARSIAN FINAL Windows desktop bundle** می‌تواند artifact آزمایشی بسازد. فقط پس از موفقیت workflow و نصب در ماشین مجازی تمیز، فایل MSI/EXE را قابل نصب تلقی کنید.

**محدودیت فعلی:** برنامه Windows هنوز پوسته دسکتاپ با احراز هویت Bearer و ذخیره نشست در Windows Credential Manager است؛ صف آفلاین محلی رمزگذاری‌شده و گردش‌کار کامل آفلاین Windows تکمیل/تأیید نشده است.

## ۹. پشتیبان‌گیری و بازیابی

- خروجی JSON افزونه از مسیر مدیریتی `GET /backup/export` و اعتبارسنجی غیرمخرب آن از `POST /backup/validate` در دسترس است.
- این خروجی به‌تنهایی نسخه پشتیبان کامل هاست نیست و عملیات Restore خودکار ندارد.
- فایل‌های رسانه‌ای، uploads، فایل‌های پیکربندی و برخی اطلاعات امنیتی/توکن‌ها در خروجی افزونه قرار نمی‌گیرند.
- برای پشتیبان کامل، از دیتابیس و کل پوشه WordPress در سطح هاست نسخه پشتیبان رمزگذاری‌شده بگیرید.
- بازیابی را فقط روی Staging جداگانه تمرین کنید و صحت ورود، تعداد رکوردها و تراز مالی را بعد از Restore کنترل کنید.

## ۱۰. چک‌لیست پذیرش قبل از Production

تمام موارد زیر باید با نتیجه ثبت‌شده PASS شوند:

- [ ] PHP lint کل افزونه روی آخرین commit.
- [ ] اجرای schema acceptance و migration روی Staging.
- [ ] اجرای تست‌های auth/sync و finance-ledger با WP-CLI و دیتابیس واقعی آزمایشی.
- [ ] تست مجوزهای نقش‌ها و جلوگیری از مشاهده داده سایر فروشندگان.
- [ ] تست idempotency، درخواست تکراری، تعارض همزمان و بازیابی پس از قطع اینترنت.
- [ ] تطبیق دفتر کل، دفتر تفصیلی، دریافتنی/پرداختنی و تراز آزمایشی با fixtureهای مستقل.
- [ ] تست چرخه چک، برگشت چک، تخصیص دریافت به فاکتور و مغایرت بانکی.
- [ ] تست موجودی، رزرو، تحویل و بهای تمام‌شده.
- [ ] تست APKهای امضاشده روی دستگاه واقعی و نصب/ارتقای Windows در VM تمیز.
- [ ] تست پشتیبان کامل دیتابیس + فایل‌ها و تمرین Restore.
- [ ] ثبت نسخه، commit، SHA-256 و فایل‌های خروجی نهایی.
- [ ] تأیید کتبی مالک سامانه برای انتشار Production.

تا پیش از تکمیل این چک‌لیست، نصب روی `pgtparts.ir`، ثبت اطلاعات واقعی مالی، صدور اسناد واقعی یا اتکا به موجودی/مانده‌های سامانه توصیه نمی‌شود.
